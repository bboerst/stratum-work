# Height

The height of the block a template builds, read from the coinbase the pool sent (BIP34): the coinbase input's
scriptSig starts with the height.

**The rule.** In `coinbase1`: version, an optional segwit marker, exactly one input with the null prevout (32 zero
bytes and index `ffffffff`), the scriptSig length, then the scriptSig's first item:
- a push of 1 to 8 bytes, read as a little-endian number with its sign bit clear (a set sign bit is a negative number,
  never a height); or
- `OP_1` to `OP_16`, for heights 1 to 16.

Anything else (`OP_0`, a non-push opcode, a longer push, a push cut short by the end of `coinbase1` or the scriptSig,
another input) gives no height, stored as 0. Nothing is guessed.

**One rule, two implementations.** The collector applies it when it stores a template (`collector-go/coinbase.go`),
and the web applies it when it shows one (`web/utils/coinbaseParser.ts`). Both are tested against the same cases,
[`testdata/coinbase-height-vectors.json`](../testdata/coinbase-height-vectors.json) (generated by
`testdata/gen_coinbase_height_vectors.py`), and a change to either that disagrees fails the tests. The one deliberate
difference is recorded there: a height past 2^53, which only a 7- or 8-byte push can hold, isn't exact as a JavaScript
number, so the web shows none.

Another chain's templates can carry a height far from Bitcoin's (in the tens of thousands, or in the millions): this
is the height its own chain gives. Judge a template's chain by its parent, not by this number (see the
[methodology](methodology.md)).
